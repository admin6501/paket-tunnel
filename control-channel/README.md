# کانال کنترلی (تونل DNS)

## چرا

چیزی که موقع قطعی واقعاً آزاردهنده است، خودِ قطع‌شدن تونل نیست — این است که
دیگر راهی برای رسیدن به سرور خارج و درست‌کردنش نداری. تا وقتی مسیر برگردد، کور
نشسته‌ای.

این کانال ترافیک واقعی حمل نمی‌کند. کارش فقط این است که وقتی همه‌چیز خوابید،
یک شل به سرور خارج بدهد.

## چرا DNS

در قطعی سراسری، gateway به حالت whitelist می‌رود، ولی `UDP/53` باید کار کند
وگرنه سرویس‌های داخلی هم می‌خوابند. اگر دامنه‌ای داشته باشی که رکورد `NS` آن به
سرور خارجت اشاره کند، ریزالور داخلی کوئری‌های recursive آن دامنه را برای تو
بیرون می‌فرستد. همان مسیر می‌شود کانال داده.

نکته: ریزالور نمی‌داند دارد چه کار می‌کند — فقط دارد کار عادی خودش را می‌کند.
به همین دلیل این کانال معمولاً آخرین چیزی است که می‌میرد.

## جهت

| نیمه | کجا | چون |
|---|---|---|
| `server` | سرور خارج | باید از بیرون قابل‌دسترس باشد و SSH خودش را expose کند |
| `client` | سرور ایران | جایی که کوئری DNS از آن بیرون می‌رود |

در نت ملی مسیرهای داخلی زنده می‌مانند، پس سرور ایران از داخل در دسترس توست.
چیزی که از دست می‌دهی سرور خارج است — و این کانال دقیقاً همان را برمی‌گرداند.

## راه‌اندازی

### ۱) دامنه

یک زیردامنه لازم داری که به سرور خارج delegate شده باشد. دو رکورد روی زون
`example.com`:

```
t.example.com.     IN  NS  tns.example.com.
tns.example.com.   IN  A   <IP سرور خارج>
```

رکورد `NS` کار اصلی را می‌کند: هر ریزالوری در دنیا که کوئری `*.t.example.com`
بگیرد، به سرور تو ارجاع می‌دهد.

> دامنه‌ای انتخاب کن که برای چیز دیگری استفاده نمی‌کنی. اگر این کانال روزی
> شناسایی شود، دامنه می‌سوزد.

### ۲) سمت خارج

```bash
sudo ./control-channel/setup-dnstt.sh server \
  --domain t.example.com \
  --forward 127.0.0.1:22
```

کلید عمومی‌ای که چاپ می‌کند را بردار.

### ۳) سمت ایران

```bash
sudo ./control-channel/setup-dnstt.sh client \
  --domain t.example.com \
  --pubkey <کلید عمومی مرحله ۲>
```

### ۴) استفاده

```bash
ssh -p 7000 root@127.0.0.1              # شل
ssh -p 7000 -D 1080 -N root@127.0.0.1   # SOCKS روی 1080
```

## انتظارات واقع‌بینانه

- **پهنای باند:** چند ده تا چند صد کیلوبیت بر ثانیه. برای وب بی‌فایده است.
- **تأخیر:** بالا و ناپایدار — هر بسته دو بار از یک ریزالور رد می‌شود.
- **کافی است برای:** شل، ویرایش کانفیگ، `systemctl restart`، دیدن لاگ.
- **کافی نیست برای:** هر چیزی که پهنای باند می‌خواهد.

## اگر UDP/53 هم بسته باشد

بعضی شبکه‌ها فقط اجازه می‌دهند با ریزالور خودشان حرف بزنی و بقیه‌ی ترافیک ۵۳ را
می‌بندند. آن حالت هم کار می‌کند — کوئری را از همان ریزالور رد کن:

```bash
sudo ./control-channel/setup-dnstt.sh client --domain t.example.com \
  --pubkey <key> --resolver 10.202.10.10
```

اگر مسیر UDP کلاً بسته باشد ولی HTTPS به یک DoH endpoint باز باشد:

```bash
sudo ./control-channel/setup-dnstt.sh client --domain t.example.com \
  --pubkey <key> --doh https://cloudflare-dns.com/dns-query
```

DoH فقط وقتی جواب می‌دهد که آن endpoint در دسترس باشد — که در قطعی سراسری
معمولاً نیست. UDP از طریق ریزالور داخلی گزینه‌ی مقاوم‌تری است.

## تست کن، قبل از اینکه لازم شود

این چیزی نیست که بشود وسط قطعی راه انداخت — رکورد DNS زمان propagation می‌خواهد
و بدون دسترسی به پنل دامنه کاری از پیش نمی‌رود. همین حالا بالا بیاور و ماهی
یک‌بار تستش کن.
